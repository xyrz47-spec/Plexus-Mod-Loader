## 측정 3 — 힙을 고정한 서버 틱 시간·힙·GC (2026-10-21)

| 항목 | 값 |
|---|---|
| 명령 | `.\gradlew.bat :poly-bootstrap:tickBenchmark -PtickBenchmarkHeap=2g` |
| 시나리오 | 측정 2와 같지만, 정육면체를 돌 대신 **유리**로 채웁니다. 돌로 채우면 매 틱 조명 계산이 쌓이는데, 조명 엔진이 따라가지 못해 대기열이 실행 내내 커졌습니다. 그래서 힙 수치가 로더가 아니라 그 경쟁을 재고 있었습니다. 유리와 공기는 빛 속성이 같아서 조명 작업이 생기지 않습니다 |
| 힙 | 양쪽 모두 `-Xms2g -Xmx2g` |
| 힙 지표 | 측정 2의 "사용 중 힙 최댓값"에 더해, JFR `jdk.GCHeapSummary` 가운데 `when = "After GC"`인 이벤트의 최댓값을 봅니다. GC 직후에도 남아 있는 힙이라서, 각 변형이 실제로 붙잡고 있는 메모리를 보여 줍니다 |
| 비교·틱 측정·반복·환경 | 측정 2와 같습니다(Poly 모드 로더 0.1.0-alpha.1, 커밋 `49e54ec` 이후) |
| 원시 데이터 | [`benchmarks/2026-10-21-ticks-fixed-heap.json`](benchmarks/2026-10-21-ticks-fixed-heap.json) |

실행 5회의 중앙값(괄호 안은 실행 간 표준편차):

| 지표 | 바닐라 | Poly 모드 로더 |
|---|---|---|
| 실행당 측정 틱 수 | 1,006 | 1,007 |
| 틱 p50 (ms) | 12.97 (±2.23) | 12.25 (±1.44) |
| 틱 p95 (ms) | 15.60 (±2.94) | 14.48 (±1.01) |
| 틱 p99 (ms) | 18.12 (±3.25) | 15.85 (±0.94) |
| 가장 긴 틱 (ms) | 58.7 | 50.7 |
| 50ms를 넘은 틱 (%) | 0.10 | 0.10 |
| 피크 힙 사용량 (MiB) | 1,283.9 (±0.5) | 1,283.4 (±0.3) |
| GC 직후 힙 최댓값 (MiB) | 158.1 (±12.7) | 157.4 (±10.7) |
| GC 횟수 | 18 (±0.5) | 18 (±0.5) |
| GC 정지 합계 (ms) | 365.3 (±62.5) | 368.3 (±56.6) |
| 가장 긴 GC 정지 (ms) | 48.4 | 46.3 |

**결론:** 힙을 고정하자 피크 힙의 표준편차가 1,141 MiB(측정 2)에서 1 MiB 아래로 줄었습니다. 이제 메모리를 비교할 수 있습니다. GC 직후 힙(바닐라 158.1, Poly 모드 로더 157.4 MiB), GC 횟수, 정지 시간은 차이가 표준편차보다 훨씬 작습니다. 이 시나리오에서 Poly 모드 로더가 붙잡는 메모리를 바닐라와 구분할 수 없습니다.

- 틱 시간 중앙값은 Poly 모드 로더 쪽이 p50 0.7ms, p95 1.1ms, p99 2.3ms 낮습니다. 하지만 어느 차이도 바닐라 쪽 실행 간 표준편차(2.2~3.3ms)보다 작습니다. 두 변형 모두 다섯 번째 실행이 유난히 빨랐습니다(p50 8.2·9.3ms). 이는 기계 상태의 영향입니다. **개선으로 주장하지 않습니다.**
- 피크 힙(약 1,284 MiB)은 두 변형이 같습니다. 2 GiB 힙에서 G1이 영 영역을 다 채우고 수집하는 지점이기 때문입니다. 메모리 비교에는 GC 직후 값을 씁니다.

- 평균 FPS 차이(−12.6%)는 표준편차와 비슷한 크기라 따로 주장하지 않습니다. p95·p99는 Poly 모드 로더 쪽 중앙값이 낮지만 표준편차 안이라 개선으로 주장하지 않습니다.

- 이 작업의 첫 실행 때 개발 PC가 블루스크린(버그체크 0xD1, 드라이버 오류)으로 재부팅됐습니다. 이전 창이 닫힌 지 1초 만에 다음 창을 여는 순간이었습니다. 그 뒤 창 사이 대기(`-PframeBenchmarkCooldown`, 기본 20초)와 실행별 결과 기록(`runs.jsonl`)을 넣었고, 이 측정은 그 상태로 끝까지 돌았습니다.

- 가장 긴 틱과 가장 긴 GC 정지는 Poly 모드 로더 쪽이 깁니다(실행마다 52~66ms). 한 번씩 있는 GC 정지로 보이며 중앙값 차이만 봅니다.
- 첫 틱 측정 시도(같은 날)에서 Poly 모드 로더 쪽 마지막 실행 하나가 모드 생성 중 멈춰 시간 초과로 끝났습니다. 같은 멈춤이 뒤의 `corpusNeoForge`(26.1.2)에서 다시 나타나 스레드 덤프를 얻었습니다. 게임 클래스로더와 FML 플러그인 클래스로더 사이의 교착이었고(Kotlin 모드 둘이 병렬로 생성될 때) 고쳤습니다([`plans/NEOFORGE_FULL_SUPPORT.md`](plans/NEOFORGE_FULL_SUPPORT.md) "N12"). 위 수치는 고치기 전에 잰 것이며, 고친 코드는 클래스를 찾는 동안 잠금을 덜 쥘 뿐 같은 일을 합니다.

## 측정 10 — 측정 9의 틱 꼬리 지연 원인 조사와 틱 다시 재기 (2026-10-24)

측정 9에서 Poly 모드 로더의 틱 p95·p99가 Connector보다 높았고 p95는 바닐라보다도 높았습니다. 그 원인을 프로파일로 찾고, Poly 모드 로더 몫이면 고친 뒤 **틱만** 같은 설정으로 다시 쟀습니다. 결론부터: **틱 안에서 Poly 모드 로더가 더하는 비용은 찾지 못했고, 그래서 로더 코드는 바꾸지 않았습니다.** p95 차이는 측정 구간 앞쪽(틱 200~399), JIT가 아직 수렴하는 동안에 몰려 있고, p99 차이의 절반가량은 측정 구간에 든 GC 한 번의 차이입니다.

### 프로파일 방법

- 측정 9의 원시 JFR 기록 15개(기본 설정, Java 샘플 20ms 간격)를 다시 분석했습니다. 측정 구간은 서버 스레드에서 `GameTestServer.tickServer`가 처음 샘플된 시각부터 잡았습니다.
- 느린 틱과 보통 틱을 나누려고 측정 도구에 켜고 끄는 옵션을 더했습니다(기본값 꺼짐): `-PtickBenchmarkTickEvents=true`는 틱 프로브가 틱마다 JFR 이벤트 `poly.TickProbe.Call`(걸린 시간, 순번)을 남기게 하고, `-PtickBenchmarkJfrSettings=<default|profile|.jfc>`는 기록 설정을 바꿉니다. 세 변형에 똑같이 들어갑니다.
- 프로파일 실행: `tickBenchmarkConnector -PtickBenchmarkHeap=4g -PtickBenchmarkRuns=2 -PtickBenchmarkTickEvents=true -PtickBenchmarkJfrSettings=<profile 기반 .jfc>`(Java 샘플 5ms, `jdk.ClassLoad` 켬, `jdk.Compilation` 문턱 0ms, safepoint·VM 작업, 모니터 1ms·park 2ms 문턱). 첫 측정 실행은 다른 작업의 게임 JVM과 겹쳐 버렸고, 변형마다 예열 실행과 두 번째 실행만 썼습니다. **프로파일 실행의 수치는 측정 결과로 쓰지 않습니다**(프로파일러 비용이 들어 있음).
- 느린 틱 = 실행마다 틱 200 이후의 p95 이상, 보통 틱 = p40~p60. 두 묶음 안에 든 샘플·할당·GC·클래스 로드·역최적화·컴파일·잠금 대기를 셌습니다.

참고로 Poly 모드 로더 쪽에만 보인 할당이 하나 있습니다: Collective(Fabric 판)의 Mixin `Level_updateNeighborsAt`이 `CallbackInfo`를 실행당 약 35MiB(전체 할당의 0.4%) 만듭니다. 모드 자신의 비용이고 Poly 모드 로더가 바꿀 일이 아니며, 크기로 보아 꼬리 지연의 원인도 아닙니다.

### 고친 것

로더 코드는 고치지 않았습니다. 프로파일에서 Poly 모드 로더 자신의 비용을 찾지 못했기 때문입니다. 바뀐 것은 측정 도구뿐입니다(위 프로파일 옵션, 기본값 꺼짐, 아래 측정에는 쓰지 않음).

**결론:**

- **전후 비교: 개선 없음.** 로더 코드를 바꾸지 않았으므로 이것은 다시 잰 것입니다. Poly 모드 로더의 p95 10.91 → 10.73ms, p99 13.97 → 14.18ms로 표준편차 안이고, 측정 9를 재현했습니다.
- **틱 p95·p99: Poly 모드 로더가 여전히 이기지 못했습니다.** p95 중앙값은 Connector가 0.66ms 낮고, Connector 일곱 실행 중 다섯(9.88~10.10ms)이 Poly 모드 로더의 모든 실행(10.45~12.01ms)보다 낮습니다. 나머지 둘(13.61, 14.84ms)은 Poly 모드 로더의 모든 실행보다 높습니다. 표준편차(2.09ms)가 차이보다 커서 규칙상 **유의한 차이 없음**이지만, 보통의 실행에서 Connector가 낮다는 모양은 측정 9와 같습니다. p99도 같습니다(차이 1.11ms, Connector 표준편차 2.36ms).

- **흔들림:** Poly 모드 로더는 세 변형 중 실행 간 흔들림이 가장 작습니다(p95 표준편차 0.66ms 대 바닐라 1.61ms, Connector 2.09ms). 바닐라 1회, Connector 2회는 실행 전체가 느렸습니다(p50 9.3~9.6ms).
- **메모리:** GC 직후 힙은 측정 9와 같습니다(Poly 모드 로더 173.1MiB, Connector 203.8MiB, 다섯·일곱 실행 모두 겹치지 않음).
