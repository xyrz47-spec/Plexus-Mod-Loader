# 설계 결정 (ADR)

Poly 모드 로더의 중요한 설계 결정은 ADR(Architecture Decision Record)로 남깁니다. 각 ADR 원문은 이 폴더에 있습니다. ADR-0001부터 ADR-0010까지는 2026-10-19에, ADR-0011~0018은 2026-10-21에, ADR-0020과 ADR-0022는 2026-10-22에, ADR-0023~0025는 2026-10-23에, ADR-0027은 2026-10-24에 채택됐습니다. ADR-0019와 ADR-0021은 제안 상태입니다.

| 번호 | 제목 | 결정 | 주요 결과 |
|---|---|---|---|
| 0001 | 첫 대상 버전 — Minecraft 26.2, Java 25 | 첫 대상 버전을 Minecraft 26.2로 정합니다. | 26.x는 난독화가 없어 매핑 계층이 필요 없습니다. Java 25 toolchain이 모든 모듈에 적용됩니다. 다음 버전은 새 어댑터 모듈을 추가해 지원하며, 26.2 어댑터의 규칙을 자동으로 재사용하지 않습니다. |
| 0002 | 빌드와 개발 환경 | Gradle Wrapper 9.8.1(체크섬 고정), Kotlin DSL과 버전 카탈로그, Java로 작성한 `build-logic` 규약 플러그인, 자체 Minecraft 개발 플러그인 `poly.minecraft-dev`를 씁니다. | 모든 모듈이 `-Xlint:all -Werror`, JUnit, Spotless를 함께 씁니다. Minecraft 파일은 manifest의 해시로 검증해 Gradle 캐시에 두고 저장소에는 넣지 않습니다. Mojang manifest 형식이 바뀌면 플러그인을 고쳐야 합니다. |
| 0003 | 클래스 변환 개입점 — 자체 게임 클래스로더 | Java agent 대신 `GameClassLoader`가 게임 jar와 모드 jar의 클래스를 child-first로 정의하고, 정의하기 전에 변환합니다. | 변환 범위가 게임 jar와 모드 jar로 한정됩니다. Poly 모드 로더 패키지는 부모 로더에서만 가져와 모드와 Poly 모드 로더가 같은 API 클래스를 공유합니다. 리소스 조회는 아직 부모 우선입니다. |
| 0004 | 변환 엔진 | 변환 규칙을 데이터로 선언하고, 게임 시작 전에 계획을 확정하며, 닫힌 동작 집합을 ASM 트리 API로 적용합니다. | 검사에 실패한 규칙은 거부되어 일부만 적용되는 일이 없습니다. 같은 메서드를 고치는 규칙은 모두 거부합니다. 프레임은 다시 계산하지 않고, 입력 바이트는 수정하지 않으며 전후 해시를 보고합니다. |
| 0005 | Minecraft와 공유하는 라이브러리 버전 고정 | gson·slf4j-api를 Minecraft version manifest와 같은 버전으로 고정하고, 로깅은 API(slf4j)만 의존합니다. | Poly 모드 로더와 게임 로그가 한 log4j 컨텍스트, 한 `logs/latest.log`에 기록됩니다. Minecraft 버전을 바꿀 때 이 고정값도 함께 검토해야 합니다. |
| 0006 | 시스템 교체 | 교체는 `poly.mod.json`의 `replacesSystems`에 권한과 함께 선언하고, 충돌은 모드 코드가 실행되기 전에 해결합니다. | 구현체는 생성 즉시 검증하며, 실패하면 기본 구현으로 되돌아가지 않고 시작을 멈춥니다. 게임 연결은 버전 어댑터의 훅이 맡아, 모드 코드는 Minecraft 클래스를 참조하지 않습니다. |
| 0007 | 변환 캐시와 모드 선언 변환 | 결과를 바꿀 수 있는 모든 입력을 담은 SHA-256 키로 변환 결과를 캐시하고, 모드는 권한을 받아 `transforms`로 규칙을 선언합니다. | 캐시는 별도의 무효화 절차가 필요 없고, 손상된 항목은 지운 뒤 다시 변환합니다. 모드 규칙은 내장 규칙과 같은 계획 단계를 거치며, 내장 규칙과 같은 메서드를 고치면 둘 다 거부됩니다. |
| 0008 | 모드 개발 SDK | 모든 모듈을 Maven으로 발행하고, `dev.polymodloader.mod` Gradle 플러그인과 독립 프로젝트 템플릿을 제공합니다. | 공개 저장소가 정해지기 전까지 Maven Local을 쓰므로, 다른 PC에서는 먼저 Poly 모드 로더를 발행해야 합니다. JavaDoc 검사가 `check`에 연결되어 공개 API 문서 오류가 빌드를 실패시킵니다. |
| 0009 | 로더 브리지 | 브리지는 `ServiceLoader`로 찾는 SPI이며 진단을 우선하고, Fabric은 엔트리포인트만 쓰는 모드부터 실행합니다. | 막는 발견 항목이 하나라도 있으면 `BLOCKED`로 보고하고 모드를 로드하지 않습니다. FML 계열(NeoForge, MinecraftForge)은 진단만 합니다. |
| 0010 | Native API와 게임 계층 | 모드용 API는 게임 타입을 노출하지 않고, 버전별 게임 계층이 Minecraft jar에 컴파일되어 그 API를 구현합니다. | 게임 계층은 Poly 모드 로더 패키지 가운데 유일하게 게임 클래스로더가 정의합니다. 모드는 선언만 하고 게임 계층이 실행합니다. 게임 연결은 모두 선언형 변환 규칙이며 실패 정책은 `ABORT_STARTUP`입니다. |
| 0011 | 여러 Minecraft 버전 지원 | 지원 버전 목록을 `gradle/minecraft-versions.properties` 한 곳에 두고, 버전마다 `poly-version-adapter-v<id>`와 `poly-game-v<id>` 두 모듈을 둡니다. | 새 버전 지원은 목록 한 줄, 복사로 만든 모듈 두 개, 게임이 실제로 바뀐 부분만 고칩니다. Native API만 쓰는 모드는 와일드카드 버전으로 다시 빌드하지 않고 새 버전에서 동작합니다. 대신 게임 계층 코드가 버전마다 복사되어, 버그를 고치면 각 버전에 반영해야 합니다. |
| 0012 | 이름 변경 — PolyLoader | Void Mod Loader(VML)를 PolyLoader로 바꾸고, 패키지·모듈·메타데이터 파일·오류 코드·모드 ID까지 모든 식별자를 `poly` 접두사로 바꿉니다. | 이전 이름을 읽는 호환 계층은 없습니다. 오류 코드는 접두사만 바뀌고 번호와 의미는 그대로입니다. 모드 템플릿을 쓰려면 Maven Local에 다시 발행해야 합니다. |
| 0013 | 변환 순서 계약, call-site 변경, 접근 확대, 캐시 상한 | 같은 메서드의 규칙은 `after`가 하나의 순서를 정할 때만 함께 적용합니다. `RedirectCall`과 Fabric과 같은 뜻의 접근 확대를 추가하고, 변환 캐시를 256 MiB로 제한합니다. | 모드가 Poly 모드 로더 내장 훅과 같은 메서드를 고칠 수 있습니다. 숫자 우선순위는 두지 않습니다. 게임 타입이 든 훅을 쓰는 모드를 위한 컴파일용 jar는 아직 없습니다. |

| 0014 | 로더를 넘는 의존성 해석과 시작 전 링크 검사 | 브리지는 의존성을 보고만 하고, 런타임이 Native·외부 모드를 함께 판정하며 차단을 연쇄 적용합니다. 로드하려는 외부 모드는 바이트코드 참조를 게임 jar와 대조합니다. | 서로 의존하는 Native·Fabric 모드를 함께 쓸 수 있고, 실행할 수 없는 모드는 게임 도중이 아니라 시작 전에 이유와 함께 제외됩니다. 실제 인기 모드를 돌리려면 Mixin·FML이 여전히 필요합니다. |

| 0015 | Fabric 중첩 jar(jar-in-jar) | 중첩 jar를 내용 해시로 풀어 각각 하나의 모드로 판정하고, 바깥 모드가 로드될 때만 안쪽도 로드하며, 같은 모드의 사본은 하나(직접 설치 > 최고 버전)만 씁니다. | 중첩 jar 자체로는 차단하지 않고 모듈 단위 이유가 나옵니다. 일부만 로드되는 바깥 모드는 경고합니다. 추출본 정리는 아직 없습니다. |
| 0016 | Fabric Loader 런타임 API | 브리지 jar에 Fabric Loader 공개 API만 담고, `FabricLoaderImpl`·`DefaultLanguageAdapter` 대체본이 Poly 모드 로더 구현으로 답합니다. 언어 어댑터는 선언한 모드가 제공하는 의존성으로 다룹니다. | `FabricLoader.getInstance()`를 쓰는 모드가 동작합니다. 뜻이 불분명한 `getGameInstance`·`getMappingResolver`는 쓰는 모드를 막습니다. Loader 버전을 올릴 때 API 닫힘을 다시 확인해야 합니다. |
| 0017 | Launcher 프로필 설치 | 설치 프로그램이 런처 폴더에 Poly 모드 로더 라이브러리, 바닐라를 상속하는 버전, 프로필을 씁니다. `poly.gameJar`가 없으면 클래스 경로에서 `version.json`이 있는 jar를 게임 jar로 씁니다. | 플레이어가 공식 런처로 Poly 모드 로더를 실행합니다. 게임 jar가 시스템 클래스로더에도 보이지만 게임 클래스는 자식 우선으로 한 벌만 쓰입니다. 실제 런처 실행 기록은 아직 없습니다. |
| 0018 | Fabric class tweaker를 접근 확대로 적용 | `accessWidener` 파일을 Fabric Loader 0.19.5와 같은 문법으로 읽고, 접근 줄을 Fabric의 암묵적 클래스 접근까지 포함해 접근 확대로 바꿉니다. 대상은 링크 검사가 게임 jar와 대조합니다. 생성자 `extendable`을 허용하도록 ADR-0013을 고칩니다. | class tweaker만으로 막히던 모드가 로드됩니다. `inject-interface`·`extend-enum`, `official`이 아닌 이름 공간, 형식 오류, 없는 대상은 각각 새 코드(`POLY-COMPAT-125..128`)로 막습니다. `102`는 폐기합니다. |
| 0019 | 난독화된 Minecraft 버전 지원(26.1 이전) — **제안** | 1.14.4~1.21.11은 Mojang 공식 매핑으로 게임 jar를 Mojang 이름으로 다시 매핑해 그 jar를 실행합니다(선택지 A). 공식 매핑이 없는 1.8.9·1.12.2는 범위에서 뺍니다. 모든 버전을 Java 25로 실행합니다. | 게임 계층·변환 규칙·링크 검사가 26.x와 같은 이름 공간을 씁니다. 매핑과 다시 매핑한 jar는 사용자 PC에서만 만들고 배포하지 않습니다. 1.21.11 전용 서버 PoC가 통과해야 채택합니다. 아직 구현은 없습니다. |
| 0020 | Fabric 모드를 Fabric Loader처럼 실행 | FabricMC Mixin 0.17.4와 MixinExtras 0.5.5를 Poly 모드 로더 Mixin 서비스로 붙이고, Fabric Loader와 같은 순서로 환경 제거·인터페이스 주입·Mixin을 적용합니다. Fabric 진입점은 Fabric과 같은 게임 내 지점에서 실행하고, 외부 모드가 있으면 게임 라이브러리도 게임 클래스로더가 맡습니다. 내장 규칙은 바닐라 호출을 남기거나(`InvokeHookAtCall`) Mixin 뒤에 적용합니다. ADR-0003·0014·0018의 일부를 고칩니다. | 실제 인기 Fabric 모드 99개가 실제 서버 시작을 통과하고, 97개가 게임 테스트 서버에서 월드 생성·틱·저장까지 됩니다. Poly 모드가 Fabric 모드에 의존해도 그 초기화가 먼저 끝난다는 보장은 없어졌습니다. 클라이언트 실행은 따로 검증해야 합니다. |
| 0021 | Forge 모드를 Forge 자신의 코드로 실행 — **제안** | 사용자 PC에서 Forge 바이너리 패치를 적용한 게임 jar를 만들고, `fmlcore`·`javafmllanguage`·`eventbus`·Forge `universal.jar`는 그대로, `fmlloader` 상태 클래스만 Poly 모드 로더 대체본으로 둡니다. 처음에는 Fabric 모드와 함께 넣으면 Forge 쪽을 막습니다. | 아직 구현은 없습니다. 패치된 jar 생성(G2)과 Forge 자신만으로 서버 시작(G3) PoC가 통과해야 채택합니다. |
| 0022 | 모든 모드 초기화 뒤의 공개 이벤트 `LifecycleEvents.MODS_INITIALIZED` | Poly 모드는 게임 시작 전에, Fabric 모드는 Minecraft 안 초기화 자리에서 초기화되므로, 모두 끝난 뒤 한 번 오는 이벤트를 둡니다. 외부 모드가 없어도 같은 자리에서 옵니다. Poly 모드의 진입점 시점은 그대로입니다. | `dependencyCrossLoader`, `nativeApiGameTests` |
| 0023 | 이름 변경 — Poly, Poly Mod Loader | 제품 이름을 Poly로, 모드 로더를 Poly Mod Loader(한국어 Poly 모드 로더)로 바꾸고, `polyloader`가 든 식별자(패키지·Maven 그룹·플러그인 ID·파일 이름·실행 핸들러)를 `polymodloader`로 바꿉니다. `poly` 접두사(모듈, `poly.mod.json`, `POLY-` 오류 코드, 모드 ID)는 그대로입니다. | `dev.polyloader`로 발행한 SDK와 그것으로 만든 모드는 다시 빌드해야 합니다. 공개 GitHub 저장소는 `xyrz47-spec/Poly-Mod-Loader`로 바뀌었고, 도메인·라이선스 이름은 그대로입니다. |
| 0024 | 설치한 Poly 모드 로더에서 Forge 파일 시스템을 JVM 클래스 경로에 두기 | Poly 모드 로더의 Java agent(`SystemClassPathAgent`)가 `Instrumentation`만 기억합니다. 런처 프로필은 `-javaagent:${library_directory}/…`, 서버의 `polymodloader-server.jar`는 `Launcher-Agent-Class`로 시작합니다. Forge 모드가 있을 때만 받은 Forge의 `securemodules`·`unsafe`·`JarJarFileSystems`·`roimfs`를 시스템 클래스로더에 더하고, 그 뒤에야 Java의 파일 시스템 목록을 확인합니다. | 설치한 런처 프로필과 전용 서버에서 Forge 모드가 실행됩니다. Forge 모드가 없으면 받는 것도 클래스 경로 변화도 없습니다. 예전 설치 프로그램으로 만든 설치는 `POLY-COMPAT-206`이 다시 설치하라고 알립니다. |
| 0025 | 다른 로더의 모드를 호스트 로더의 모드 목록에 보이기 | 호스트(Forge)가 실행하는 모드는 `GameHost.mods()`로 Fabric Loader의 모드 목록에 루트 경로 없이 들어갑니다. Poly 모드 로더가 실행하는 모드는 `GameHost.otherMods`로 Forge에 넘어가고, FML의 `ModList.getModFileById`·`isLoaded`가 FML의 답이 없을 때만 그 모드를 forgespi 보기로 답합니다(검사한 형태일 때만 바꾸고, 다르면 `POLY-COMPAT-211`). | Physics Mod 같은 Forge 모드가 Sodium 같은 Fabric 모드를 봅니다. `getModContainerById`·`getModFiles`와 `LoadingModList`는 그대로이고, 같은 ID는 Forge가 이깁니다. 다른 로더의 모드를 보고 켜지는 선택적 연동이 새 실패를 낼 수 있습니다. |
| 0026 | NeoForge 모드를 NeoForge 자신의 코드로 실행 — **채택** | 사용자 PC에서 `NFPATCHBUNDLE001` 패치를 적용한 게임 jar를 만들고, FML의 `FMLLoader.create`를 그대로 실행하되 게임 레이어를 만드는 호출과 mods 폴더 검색만 검사한 형태일 때 Poly 모드 로더 호스트로 바꿉니다. 게임 레이어는 게임 클래스로더가 정의하고, FML의 `ClassProcessor`는 브리지 변환 단계에서 부릅니다.
