# ADR-0011: 여러 Minecraft 버전을 버전 목록 하나와 버전별 모듈 두 개로 지원한다

- 상태: 채택 (2026-10-21)
- 관련: ADR-0001(대상 버전), ADR-0005(공유 라이브러리), ADR-0010(게임 계층), 설계서 §5.5, §7.7

## 배경
지금까지는 Minecraft 26.2 하나만 지원했고, 그 버전이 여러 곳에 박혀 있었습니다.
- 버전 카탈로그의 `minecraft = "26.2"` 하나를 빌드 플러그인, 개발 실행, 모드 플러그인이 모두 읽었습니다.
- `settings.gradle.kts`와 `poly-bootstrap`이 `-v26_2` 모듈을 이름으로 직접 포함했습니다.
- 검증 작업이 기대하는 로그 줄에 `26.2`와 `GameLayer26_2`가 적혀 있었습니다.
- 모드의 `"minecraft"` 목록은 정확히 같은 버전 ID만 받았습니다. 그래서 게임 클래스를 쓰지 않는 Native 모드도 버전마다 다시 배포해야 했습니다.

런타임 구조는 이미 버전별입니다. 어댑터는 `ServiceLoader`로 찾고, 게임 jar의 `version.json`으로 고르며, 게임 계층 클래스 이름도 어댑터가 알려 줍니다(ADR-0010). 바꿀 곳은 빌드와 메타데이터였습니다.

## 결정
1. **지원 버전 목록은 `gradle/minecraft-versions.properties` 한 곳에 둡니다.**
   - `supported`: 지원 버전, 오래된 순
   - `default`: 예제, 개발 실행, 검증 작업이 쓰는 버전
   - `java.<버전>`: 그 버전이 쓰는 Java 기능 버전

   버전 카탈로그의 `minecraft`는 없앴습니다. 카탈로그의 `java`는 버전 독립 모듈의 Java이며, 지원 버전 중 가장 낮은 Java로 둡니다.
2. **버전마다 모듈 두 개를 둡니다.**
   - `poly-version-adapter-v<id>`: 실행 대상과 변환 규칙
   - `poly-game-v<id>`: 그 버전의 게임 클래스로 구현한 Native API

   `<id>`는 버전의 `.`과 `-`를 `_`로 바꾼 값입니다(26.2 → `26_2`). 패키지와 클래스 이름도 같은 규칙을 따릅니다: `…game.layer.v<id>.GameLayer<id>`, `…game.version.v<id>.Minecraft<id>Adapter`. 그래서 빌드가 이름만으로 모듈과 클래스를 찾을 수 있습니다(`MinecraftVersions`).
   - `settings.gradle.kts`는 목록의 버전마다 두 모듈을 포함합니다. 디렉터리가 없으면 만드는 명령을 알려 주고 실패합니다.
   - `poly.minecraft-compile`은 모듈 이름에서 버전을 알아냅니다. 그 버전의 jar에 컴파일하고, Java 툴체인도 그 버전에 맞춥니다.
   - `poly-bootstrap`은 모든 버전의 어댑터를 담습니다. 런타임은 게임 jar의 버전으로 어댑터를 고릅니다.
3. **실행과 검증은 한 번에 한 버전입니다.**
   - 기본은 `default`이고, `-PpolyMinecraft=<버전>`으로 바꿉니다.
   - 기대 로그 줄은 고른 버전으로 만듭니다.
   - 목록에 없는 버전을 고르면 지원 목록을 보여 주고 실패합니다.
4. **어댑터 하나가 여러 버전 ID를 맡을 수 있습니다.**
   - `GameVersionAdapter.gameVersions()`의 기본값은 `gameVersion()` 하나입니다.
   - 변환 대상과 게임 계층이 쓰는 부분이 바뀌지 않은 핫픽스(예: 26.2.1)는 이 목록에 더합니다. 하나라도 바뀌었으면 새 어댑터를 만듭니다.
5. **모드의 `"minecraft"` 목록은 패턴을 받습니다(`MinecraftVersionPattern`).**
   - 정확한 ID: `26.2`
   - 와일드카드: `26.*`, `26.2.*`, `*`
   - 범위: `>=26.2 <27`

   와일드카드와 범위는 숫자 릴리스 버전만 비교합니다. 스냅샷은 정확한 ID로만 받습니다. 형식이 틀리면 `POLY-METADATA-009`입니다.

   Native API만 쓰는 모드는 와일드카드나 범위를 씁니다. 변환 규칙처럼 특정 버전의 게임 코드에 기대는 모드는 정확한 ID를 씁니다. 저장소 예제도 이 기준을 따릅니다: Native 예제는 `26.*`, `transform-demo-mod`는 `26.2`.
6. **모드 개발 플러그인은 지원 목록을 함께 배포합니다.**
   - `dev.polymodloader.mod`는 목록을 플러그인 안에 담습니다.
   - 모드 프로젝트는 `gradle.properties`의 `polyMinecraft=<버전>`으로 실행할 버전을 고릅니다. 고르지 않으면 기본 버전입니다.
   - 실행에 쓰는 어댑터 의존성과 Java 툴체인이 고른 버전을 따릅니다.
7. **새 버전은 가장 가까운 버전을 복사해서 시작합니다.**
   - `./gradlew newMinecraftVersion -Pfrom=26.2 -Pto=<새 버전> [-Pjava=<버전>]`이 두 모듈을 복사합니다(`VersionScaffolder`).
   - 경로, 패키지·클래스 이름, 문자열 안의 버전을 바꾸고 목록에 새 버전을 더합니다. 빌드 출력과 로그는 복사하지 않습니다.
   - 버전 토큰은 통째로 일치할 때만 바꿉니다. `26.2.1`이나 `126_2`는 그대로 둡니다.
   - 그다음은 사람이 합니다: 컴파일 오류 고치기, 변환 규칙 대상을 새 jar에서 `javap`로 확인하기, 팩 형식 같은 버전 데이터 갱신, `-PpolyMinecraft=<새 버전>`으로 게임 테스트·호환성 행렬 실행. 작업이 끝나면 출력에 이 순서가 나옵니다.

## 고려한 대안
- **버전 사이에 게임 계층 코드를 공유(공통 소스 세트 + 버전별 덮어쓰기, 전처리기 주석).** 중복은 줄지만, Minecraft 클래스가 버전마다 바뀌는 곳마다 분기가 생깁니다. 또 한 버전을 고치다 다른 버전을 깨뜨리기 쉽습니다. 지금은 지원 버전이 하나라 얻는 것이 없습니다. 버전이 셋 이상이 되어 중복이 실제 부담이 되면 다시 검토합니다. 버전 독립 코드는 이미 `poly-game-api`와 `poly-runtime-impl`의 `NativeRegistrations`(검증)에 있습니다.
- **하나의 게임 계층이 반사로 여러 버전을 지원.** ADR-0010이 버린 방식입니다. 타입 검사를 잃습니다.
- **모드 메타데이터에 SemVer 범위 재사용.** Minecraft 버전은 `26.2`처럼 두 자리이거나 스냅샷 ID여서 SemVer가 아닙니다. 그래서 별도 패턴을 둡니다.

## 결과
- 새 버전 지원에 바꿀 파일:
  - 목록 파일 한 줄(작업이 자동으로 더함)
  - 새 모듈 두 개(복사로 생성)
  - 게임이 실제로 바뀐 부분

  빌드 스크립트, 플러그인, 검증 작업은 고치지 않습니다.
- 같은 Poly 모드 로더 배포가 여러 버전을 실행합니다. Native 모드는 와일드카드로 다시 빌드하지 않고 새 버전에서 돕니다. 단, 새 버전의 게임 계층이 그 모드가 쓰는 API를 모두 구현해야 합니다.
- 비용:
  - 지원 버전마다 게임 계층 코드가 복사됩니다. 버그를 고치면 각 버전에 반영해야 합니다.
  - 모든 버전의 Minecraft jar를 내려받아 컴파일하므로 첫 빌드가 길어집니다. 실제 게임 검증은 한 번에 한 버전입니다. CI에서 버전마다 `-PpolyMinecraft`로 따로 돌립니다.
- 검증:
  - 단위 테스트: `MinecraftVersionPatternTest`, `ModDependencyResolverTest`의 와일드카드·범위 경우, build-logic의 `VersionScaffolderTest`(이름 바꾸기, 건너뛰는 디렉터리, 목록 갱신, 잘못된 입력)
  - `-PpolyMinecraft=26.2`로 실제 게임 검증: 서버 부팅, 월드 저장, 게임 테스트 45개, 혼합 로더 행렬 6개
  - 목록에 없는 버전을 고르면 실패하는 것도 확인했습니다.

## 후속 (2026-10-21)
- 새 버전의 게임 파일을 직접 넣을 수 있습니다: `MinecraftFiles/<버전>/`(런처의 버전 폴더 구조) 또는 `-PpolyMinecraftFiles=<경로>`.
  `LocalMinecraftFiles`가 jar를 버전 JSON의 SHA-1로 확인한 뒤 다운로드 캐시로 복사하므로, 그 뒤의 과정(launch spec,
  `LauncherProfileLaunchTask`의 캐시 경로)은 바뀌지 않습니다. 해시가 다르면 실패하고, 없는 파일은 내려받습니다.
  검증: build-logic의 `LocalMinecraftFilesTest`.
- 26.1보다 오래된(난독화된) 버전에 필요한 매핑 계층은 아직 없습니다.

## 후속: 26.1 계열 추가 (2026-10-21)
- `supported=26.1,26.2`, `default=26.2`. 26.1은 `-v26_1` 모듈 두 개로 지원하고, 26.1.1과 26.1.2는 26.1 어댑터의 `gameVersions()`로 지원합니다. 차이는 각 모듈 README의 "26.2와 다른 점"에 있습니다.
- 4번(핫픽스)을 실제로 쓰려니 두 곳이 빠져 있었습니다.
  - 런타임: 계획기는 규칙이 적은 버전과 실행 중인 버전이 정확히 같을 때만 받습니다. 그래서 26.1 어댑터의 규칙(`"26.1"`)이 26.1.1에서 모두 거부됐을 것입니다. `AdapterTransformRules`가 고른 어댑터의 규칙 가운데 어댑터 자신의 버전을 적은 것을 실행 중인 버전으로 계획합니다. 모드의 규칙과 접근 확대는 바뀌지 않습니다.
  - 빌드: 목록 파일에 `hotfixes.<버전>=<ID>,…`를 더했습니다. 핫픽스는 모듈이 없고, `-PpolyMinecraft`로 고를 수 있으며, 설치기가 보여 줍니다(`MinecraftVersions.runnable()`, `modulesVersion()`).
- 테스트 모드와 `transform-demo-mod`는 메타데이터에 26.2를 적었습니다. 루트 빌드가 이것을 고른 버전으로 바꿔 빌드하므로, 같은 기대 로그 줄로 모든 버전을 검증합니다. 기본 버전에서는 바뀌는 것이 없습니다.
- 검증(26.1, 26.1.1, 26.1.2 각각): `serverBootSmokeTest`, `worldCreateSaveTest`, `nativeApiGameTests`(52개), `compatibilityMatrix`(11개 시나리오) 통과. 클라이언트 전용 규칙은 창을 열지 않고 클라이언트 jar에 변환 계획·적용·검증을 돌리고 훅 시그니처를 확인했습니다.
- `compatibilityCorpus`는 `compat/mod-corpus-26.2.json`만 있어 26.2에서만 돌립니다.
