# ADR-0014: 로더를 넘는 의존성 해석과 시작 전 링크 검사

- 상태: 채택 (2026-10-21)
- 관련: ADR-0009(로더 브리지), ADR-0003(게임 클래스로더), 설계서 §13, §15.4

## 배경
ADR-0009의 Fabric 브리지는 `fabric.mod.json`에 `minecraft`·`java`·`fabricloader` 말고 의존성이 하나라도 있으면 그 모드를 차단했습니다(`POLY-COMPAT-104`). 그래서 서로 의존하는 모드는 로더와 상관없이 함께 쓸 수 없었습니다. 반대로 `minecraft` 조건은 확인하지 않아서, 다른 버전용 Fabric 모드도 로드되었습니다.

Modrinth에서 26.2용 인기 모드 124개를 받아 실험했습니다(Fabric·NeoForge·Forge 각 상위 40개와 그 필수 의존 모드). 세 가지가 드러났습니다.

1. 메타데이터만으로는 판정이 부족합니다. `placeholder-api`는 차단 사유가 없어 로드됐습니다. 하지만 Fabric Loader 런타임(`FabricLoader.getInstance()`)을 씁니다. Poly 모드 로더는 Fabric Loader를 시작하지 않으므로, 다른 모드가 이 라이브러리를 부르는 순간 게임 도중에 실패합니다.
2. NeoForge 라이브러리 jar는 매니페스트의 `FMLModType`으로만 표시됩니다. 그래서 "모드가 아님"으로 잘못 분류됐습니다.
3. 브리지 코드는 JSON·TOML 값의 형식이 예상과 다르면 예외를 던졌습니다. 깨진 jar도 마찬가지였습니다. 이 예외는 진단 없이 시작을 멈추게 했습니다.

## 결정
1. **의존성은 브리지가 보고하고 런타임이 로더를 넘어 판정합니다.**
   - 브리지는 `BridgedDependency`(필수·선택·`breaks`·`conflicts`)와 `providedIds`를 돌려줍니다. 버전 조건은 그 로더의 규칙으로 판정합니다.
   - Fabric은 브리지가 이미 클래스 경로에 둔 Fabric Loader 0.19.5의 공개 API(`VersionPredicate.parse`, `Version.parse`)를 그대로 씁니다. 그래서 `~26.2`, `>=26.2-`, `1.21.x`, 배열(OR)의 뜻이 Fabric과 같습니다.
   - `CrossLoaderModResolver`가 외부 모드를 결정합니다. 외부 모드는 다음 조건을 모두 만족해야 로드됩니다.
     - 필수 의존성마다 로드되는 모드(Native든 외부든)나 환경이 있고, 버전이 맞아야 합니다. 환경은 `minecraft`, `java`, 브리지 내장 ID(Fabric `fabricloader`)입니다.
     - `breaks` 대상이 없어야 합니다.
     - 다른 모드와 ID가 겹치지 않아야 합니다.
     - 링크 검사를 통과해야 합니다.
   - 하나가 막히면 그 모드에 의존하는 모드도 막힙니다. 이 판정은 더 바뀌지 않을 때까지 반복합니다. 막힌 모드는 최종 상태를 기준으로 막힌 이유를 모두 받습니다. 예: "설치됐지만 차단됨: Fabric mod X … BLOCKED: [POLY-COMPAT-101]".
   - Native 모드는 이 결과를 받아 `ModDependencyResolver`가 판정합니다. Native 모드가 외부 모드에 의존할 수 있고, 차단된 외부 모드에 의존하면 `POLY-DEPENDENCY-009`로 이유를 알립니다. Native의 기존 정책은 그대로입니다. 오류가 있으면 게임 코드가 돌기 전에 시작을 멈춥니다.
2. **로드하려는 외부 모드는 시작 전에 바이트코드 링크 검사를 받습니다(`ModLinkVerifier`).**
   - 클래스 파일의 상수 풀에 있는 클래스·메서드·필드 참조를 JDK Class-File API로 읽습니다.
   - 참조는 이번 실행에 실제로 있는 것과 대조합니다. 대상은 게임 jar(멤버는 JVM과 같은 방식으로 상위 클래스와 인터페이스를 따라 찾음), Poly 모드 로더 클래스 경로의 JDK·라이브러리, 브리지가 제공한다고 선언한 로더 패키지(Fabric은 `net/fabricmc/api/`), 함께 설치된 모드입니다.
   - 차단하는 경우: 로더 런타임의 제공하지 않는 클래스(`111`), 이 게임 버전에 없는 Minecraft 클래스·멤버(`112`), 읽을 수 없는 클래스 파일이나 없는 JDK 클래스(`118`), 없는 엔트리포인트 클래스(`119`).
   - 차단하지 않고 기록만 하는 경우: 설치되지 않은 다른 모드의 클래스, 그리고 전용 서버에서 참조하는 클라이언트 클래스(`113`). 선택 연동 코드와 클라이언트 전용 코드가 흔하기 때문입니다.
3. **엔트리포인트는 로더를 가리지 않고 의존 순서대로 부릅니다(`CrossLoaderLoadOrder`).** 모든 모드의 common 단계를 먼저, 그다음 side 단계를 부릅니다. 각 단계에서는 필요한 모드가 먼저 돌고, 같은 조건이면 ID 순서입니다. Fabric은 순환을 허용하므로, 외부 모드가 낀 순환은 나머지 뒤에 ID 순서로 부릅니다.
4. **검색과 판정은 입력이 무엇이든 예외를 던지지 않습니다.**
   - 깨진 jar는 `POLY-DISCOVERY-003`, FML 라이브러리는 `POLY-COMPAT-205`로 보고합니다.
   - 브리지가 그래도 예외를 던지면 그 jar를 `POLY-COMPAT-002`로 차단합니다.
   - 브리지는 값마다 형식을 확인한 뒤 읽습니다.
5. `POLY-COMPAT-104`는 폐기합니다. 의미를 바꾸지 않고 새 번호 `114`~`117`이 그 역할을 나눠 맡습니다.

## 근거(실험, 2026-10-21)
- `dependencyCrossLoader`: Native 라이브러리, Native 애드온(Fabric 라이브러리 필요), Fabric 라이브러리(별칭 제공), Fabric 애드온(별칭과 Native 라이브러리 필요)이 모두 로드됩니다. 엔트리포인트가 설정한 값으로 의존 대상이 먼저 돌았음을 확인했습니다.
- `dependencyBlockedChains`: 다음 7가지 실패가 모두 이유와 함께 보고되고, 게임은 나머지 모드로 시작합니다.
  - 다른 MC 버전용 모드
  - 차단된 Fabric·NeoForge 모드와 설치되지 않은 모드에 의존하는 모드
  - 없는 게임 메서드·클래스를 참조하는 모드
  - Fabric Loader 런타임을 쓰는 모드
  - 형식이 틀린 메타데이터
  - FML 라이브러리
  - 깨진 jar
- 실제 모드 124개(`compat/mod-corpus-26.2.json`로 고정):
  - 클라이언트·서버 각각 모드 하나씩과 전부 함께 판정했고 예외는 0건입니다. 게임 테스트 서버 4조합도 모두 정상 시작했습니다.
  - 로드 가능한 모드는 0개입니다. 막는 이유는 Mixin(Fabric `101` 45개, FML `202` 34개), FML 런타임(`201` 71개), 중첩 jar(`103` 26개), class tweaker(`102` 26개)입니다.

## 결과
- 실행할 수 없는 외부 모드는 게임 코드가 돌기 전에 이유와 함께 제외됩니다. 그 모드가 필요한 모드도 함께 제외되므로, 게임 도중에 `NoClassDefFoundError`·`NoSuchMethodError`로 이어지지 않습니다. 단, 참조만 검사하고 실제 실행 경로는 분석하지 않습니다. 또 리플렉션으로 찾는 클래스는 보이지 않습니다.
- 서로 의존하는 Native·Fabric(엔트리포인트만 쓰는) 모드를 함께 쓸 수 있습니다.
- 실제 인기 모드를 실행하려면 Mixin 서비스, 중첩 jar, Fabric Loader API 구현이 필요합니다. NeoForge·Forge는 FML 런타임이 필요합니다. 이 ADR은 그 기능을 제공하지 않습니다. 다음 단계는 ADR-0009의 순서(중첩 jar → Mixin → `FabricLoader` 최소 구현)를 따릅니다.
- 링크 검사는 로드 후보마다 jar의 클래스를 한 번 읽습니다. 차단된 모드는 검사하지 않습니다.
