# PolyBoost 계획: Native API만 쓰는 성능 Poly 모드

상태: 계획(2026-10-21). 코드와 측정 결과는 아직 없습니다. 이 문서에 적힌 성능 수치는 모두 **목표**이며, `frameBenchmark`·`tickBenchmark` 결과가 나오기 전에는 "빠르다"고 쓰지 않습니다(AGENTS.md 10, `docs/PERFORMANCE.md`).

## 목표

PolyBoost는 Poly 모드 로더에서만 동작하는 성능·편의 모드입니다. Sodium(렌더링), Lithium(서버 틱), FerriteCore(메모리)가 Fabric에서 하는 역할을 Poly 모드 하나가 맡는 것이 목표입니다.

| 목표 | 기준 |
|---|---|
| 성능 | 같은 월드·같은 장면에서 바닐라보다 프레임 시간 p50·p95와 1% 저점이 유의하게 좋음. Sodium(Fabric)과 같은 장면에서 비교한 결과를 공개 |
| 편의성 | 설치 후 설정 없이 동작. 게임 안 설정 화면, 프리셋(품질·균형·성능), 기능별 끄기, 프레임 시간 HUD |
| 안정성 | 기능마다 바닐라 동작으로 되돌리는 스위치. 바닐라와 결과가 다른 경우를 게임 테스트로 고정 |
| Poly 모드 전용 | Mixin이나 Minecraft 클래스 없이 Native API와 시스템 교체만 씀. 그래서 Fabric·Forge에서는 돌지 않고, Minecraft 버전이 바뀌어도 게임 계층만 따라가면 됨 |

## 왜 바로 만들 수 없는가

- Sodium은 청크 렌더러를 통째로 다시 씁니다. 메싱 스레드, 압축 정점 형식, 다중 그리기, 가시성 그래프가 들어갑니다. 이 모든 것을 Mixin으로 게임 내부에 연결합니다.
- 지금 Native API에는 렌더링 경로를 바꿀 수 있는 교체 지점이 없습니다. 교체 가능한 시스템은 `poly:game_brand` 하나입니다(ADR-0006). 클라이언트 그리기 API(HUD, 월드 그리기, 셰이더 파이프라인)는 그림을 **더하는** 기능이지, 게임의 그리기를 **바꾸는** 기능이 아닙니다.
- 측정에도 제약이 있습니다. `frameBenchmark`는 게임 창을 12번 다시 엽니다. 이 PC에서는 그 도중에 블루스크린(0xD1)이 난 기록이 있어, 이번 작업에서는 돌리지 않았습니다.

그래서 PolyBoost는 Poly 모드 로더 본체에 **성능 시스템 계약**을 먼저 더하고, 그 계약을 구현하는 모드로 만듭니다. 이것이 Poly 모드 로더다운 방식이기도 합니다.
- 게임 계층은 계약마다 바닐라 동작을 기본 구현으로 둡니다.
- PolyBoost는 `replacesSystems`로 더 빠른 구현을 넣습니다.
- 다른 Poly 모드도 같은 계약을 볼 수 있어, 충돌을 시작 전에 진단합니다.

## 단계

각 단계는 "계약 + 바닐라 기본 구현 + PolyBoost 구현 + 게임 테스트 + 전후 측정"을 갖춰야 끝납니다. 계약을 더하는 결정은 단계마다 ADR로 남깁니다.

### 0단계 — 기준선과 Poly 모드 로더 자신의 비용

1. `frameBenchmark`에 "모드 없는 Poly 모드 로더" 변형을 더합니다. 측정 4에서 본 +0.14ms(p50)가 어디서 오는지 로더와 개발용 모드로 나눠 봅니다.
2. 로더 몫이 있으면 먼저 없앱니다. PolyBoost가 Poly 모드 로더 자신의 비용을 메우는 데 쓰이면 안 됩니다.
3. 측정 장면을 고정합니다. 저장된 벤치마크 월드, 시점, 렌더 거리 12·24, 화면 해상도를 정하고 1% 저점을 지표에 더합니다.
4. 블루스크린 문제: 창을 다시 여는 사이에 쉬는 시간(`-PframeBenchmarkCooldown`)을 늘리거나, 한 창 안에서 여러 번 재는 방식을 검토합니다.

### 1단계 — 프로파일링

- JFR로 위 장면의 클라이언트 렌더 스레드와 작업자 스레드를 기록합니다. 26.2에서 실제로 시간이 드는 곳을 순위로 정리합니다.
- 기록할 것: 청크 메싱, 청크 업로드, 엔티티·블록 엔티티 그리기, 파티클, 애니메이션 텍스처, 조명 갱신, GC 할당률.
- 이 결과로 2·3단계의 순서를 다시 정합니다. 아래 순서는 Sodium·Lithium의 공개된 설계에서 가져온 가설입니다.

### 2단계 — 위험이 낮은 계약 (클라이언트)

| 계약(가칭) | 바닐라 기본 | PolyBoost 구현 | 확인 |
|---|---|---|---|
| `poly:animated_textures` | 모든 애니메이션 텍스처를 매 틱 갱신 | 화면에 보이는 것만 갱신 | 보이는 텍스처는 바닐라와 같은 프레임을 그리는지 게임 테스트, 프레임 시간 |
| `poly:block_entity_culling` | 블록 엔티티를 거리 안에서 모두 그림 | 시야 밖·가려진 것 건너뛰기 | 상자·표지판이 많은 장면 |
| `poly:particle_culling` | 파티클을 모두 그림 | 시야 밖 파티클 건너뛰기 | 파티클 많은 장면 |
| `poly:entity_render_distance` | 엔티티 종류와 무관 | 종류별 그리기 거리 | 편의 기능, 설정 화면 |

### 3단계 — 청크 렌더링 (가장 큰 효과, 가장 큰 위험)

- 계약 `poly:chunk_mesher`(블록 → 정점), `poly:chunk_visibility`(어떤 구역을 그릴지), `poly:terrain_draw`(그리기 호출 묶기)를 설계합니다. 26.2의 Blaze3D 렌더러 구조를 `javap`로 확인한 뒤 정합니다.
- PolyBoost 구현 후보는 Sodium과 같은 방향입니다. 메싱 작업자 스레드, 압축 정점 형식, 그리기 호출 묶기, 가시성 계산 개선을 차례로 시도합니다.
- 리소스 팩·셰이더·다른 모드의 블록 모델과 맞는지 게임 테스트와 화면 비교(스크린숏 차이)로 확인합니다.

### 4단계 — 서버 틱 (Lithium 영역)

- `tickBenchmark`로 엔티티 충돌, 몹 AI 목표 선택, 블록 틱 예약, 관심 지점(POI) 조회의 비용을 봅니다.
- 차례로 계약으로 만듭니다(`poly:entity_collisions` 등).
- 바닐라와 결과가 같은지, 같은 시드·같은 입력으로 상태를 비교하는 게임 테스트로 고정합니다.

### 5단계 — 편의 기능과 출시

- 게임 안 설정 화면(Native `ModScreen`), 프리셋, 기능별 끄기, 설정 파일(`config/poly_boost`)
- 프레임 시간 그래프 HUD(Native HUD 레이어)
- 출시 조건: 0~3단계의 측정 결과를 `docs/PERFORMANCE.md`에 기록하고, 같은 장면에서 Sodium(Fabric)과 비교합니다. 비교 결과가 있을 때만 "Sodium과 비슷한"이라고 씁니다.
