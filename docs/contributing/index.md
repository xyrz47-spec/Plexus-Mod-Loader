# 기여하기

Poly 모드 로더 저장소에서 작업할 때 따르는 규칙입니다. 이 섹션은 그중 자주 필요한 것을 정리합니다. 기여한 코드는 저장소의 라이선스(Mozilla Public License 2.0)로 배포됩니다.

- [개발 환경](dev-environment.md): JDK, IntelliJ IDEA, 저장소 위치
- [빌드와 테스트](build-and-test.md): 검증 명령과 언제 무엇을 실행하는지
- [새 Minecraft 버전 지원하기](new-minecraft-version.md)

## 작업 원칙

1. 변경 전에 관련 모듈의 `README.md`, 설계서의 해당 절, `docs/adr/`를 읽고 책임 경계를 파악합니다.
2. 큰 기능은 가장 작은 재현 가능한 PoC부터 만듭니다. 같은 기능이 이미 있는지 먼저 검색합니다.
3. TODO와 구현 완료를 구분합니다. 완료 주장은 실행한 테스트 결과를 근거로 합니다. 빌드·테스트를 실행하지 못했으면 그 사실과 검증하지 못한 범위를 적습니다.
4. 새 공개 API에는 `@ApiStability`, JavaDoc(목적·호출 시점·스레드·실패 조건), 테스트, 예제를 함께 추가합니다.
5. 새 모듈에는 README(하는 일 / 소유 / 하지 않는 일 / 의존 / 진입점 / 빌드·테스트 / 흐름 / 제한)를 둡니다.
6. Minecraft 클래스·메서드 이름은 버전별 어댑터와 게임 계층 밖에 두지 않습니다. 공개 API(`dev.polymodloader.api.*`)에는 Minecraft 타입을 노출하지 않습니다. 대상은 실제 jar에서 확인한 뒤 적고, 추측으로 구현하지 않습니다.
7. 클래스 변환은 대상 owner·name·descriptor, 바이트코드 사전조건, 실패 정책을 갖춘 규칙으로만 선언합니다. 실패를 성공처럼 기록하지 않습니다.
8. 예외를 광범위하게 삼키지 않습니다. 테스트를 통과시키려고 검증을 지우지 않습니다.
9. `Manager`/`Helper`/`Utils` 같은 모호한 만능 클래스를 만들지 않습니다.
10. 성능 개선은 측정 전후 결과가 있을 때만 주장합니다.
11. 클래스 로딩·버전 매핑·변환 엔진·브리지 구조의 결정은 ADR로 남깁니다. [설계 결정](../adr/)을 보세요.

## 오류 코드

기존 오류 코드의 의미를 바꾸지 말고 새 번호를 추가합니다. 코드 목록은 오류 코드(문서 사이트)에 있습니다.

## 하지 말 것

- Minecraft jar나 그 일부를 저장소에 커밋하지 않습니다(`run/`, `build/`는 무시됨).
- Minecraft EULA에 사용자 대신 동의하지 않습니다.
- 비밀 값, 토큰, 개인 경로를 로그·문서·커밋에 넣지 않습니다.
- 포매터 변경과 기능 변경을 한 커밋에 섞지 않습니다.
