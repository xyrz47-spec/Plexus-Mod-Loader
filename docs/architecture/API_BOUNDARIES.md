# 렌더링·UI·네트워크·저장 API의 경계 설계 (Phase 4)

- 상태: 설계 (2026-10-19). 구현 전입니다.
- 관련: 설계서 §4.5, §5.3 G·I·J, §7.7

이 문서는 아직 구현하지 않은 네 영역에서 **무엇을 공개 API에 두고, 무엇을 버전 어댑터에 남길지**를 정합니다. 서버 생명주기 이벤트(Phase 4에서 구현)와 같은 원칙을 씁니다.
- 공개 API에는 Poly 모드 로더 타입과 읽기 전용 뷰만 둡니다.
- Minecraft 타입과의 연결은 `game.version.v26_2`의 훅과 `MethodHandle` 접근자가 맡습니다.

| 영역 | 공개 API 모듈(예정) | 공개 API에 두는 것 | 버전 어댑터에 남기는 것 | 스레드 규칙 | 첫 구현 후보 |
|---|---|---|---|---|---|
| 렌더링 | `poly-render-api` | 렌더 단계 이벤트(`WORLD_AFTER_ENTITIES`, `HUD`), 단계별 그리기 컨텍스트(Poly 모드 로더 타입) | `GameRenderer`/`LevelRenderer` 호출 지점 훅, 그래픽 상태 저장·복원 | 렌더 스레드 전용, 호출 사이 상태 누수 금지 | HUD 텍스트 그리기 이벤트 |
| UI·입력 | `poly-ui-api` | 키 바인딩 등록, 화면 열기/닫기 이벤트, 간단한 화면 구성 요소 | `Screen`·`KeyMapping` 생성과 등록, 옵션 파일 저장 | 클라이언트 메인(렌더) 스레드 | 키 바인딩 등록 |
| 네트워크 | `poly-network-api` | 채널 ID, 직렬화 계약(`PayloadCodec`), 크기 상한, 수신 측 권한 검사 콜백 | 커스텀 페이로드 등록, 연결 단계 협상 | 수신은 네트워크 스레드, 게임 상태 변경은 서버 스레드로 넘김 | 버전 협상이 있는 단일 채널 |
| 저장 | `poly-persistence-api` | 모드별 데이터 스키마 버전, 마이그레이션 단계 등록(`world.data.migrate` 권한), 저장·불러오기 이벤트 | 월드 저장 형식(NBT) 변환, 저장 시점 훅 | 서버 스레드, 저장 중 비동기 금지 | 월드별 키-값 데이터와 스키마 버전 |

## 공통 규칙
1. 각 API의 첫 버전은 `PREVIEW`입니다. 버전 어댑터 연결부는 `VERSION_BOUND`입니다.
2. 네트워크·저장 API는 **버전 관리와 마이그레이션 없이는 공개하지 않습니다**(설계서 §5.3 J, §18).
3. 사용자 데이터를 덮어쓰는 마이그레이션은 백업을 만든 뒤에만 실행합니다(§18).
4. 실제 게임 검증 방법: 서버 측 API는 게임 테스트 서버, 클라이언트 측 API는 `clientWorldReloadTest`와 같은 방식의 창 실행 검증을 씁니다.
